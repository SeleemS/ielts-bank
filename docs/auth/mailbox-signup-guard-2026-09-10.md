# Mailbox signup guard

This change reserves one canonical mailbox per new account, closing `name+tag@domain` repeat-signup and email-change bypasses without changing the address used for email delivery. Existing duplicate accounts remain intact and can log in, confirm, reset passwords, and change a plus tag within their mailbox.

Canonicalization lowercases and removes the local-part suffix beginning at `+`. It does not remove dots or equate domains (including gmail.com/googlemail.com). This is an explicit anti-abuse policy: providers that treat `+` as part of a distinct mailbox cannot register those as independent accounts. It does not prove common mailbox ownership and cannot stop independent addresses, disposable mailboxes, or other provider aliases.

`auth_mailbox_claims` has one unique row per canonical mailbox and a private UUID membership array for pre-existing duplicates. Unique-index arbitration serializes concurrent claims. New-account, profile-trigger, and email-change failure rolls the claim back with the Auth transaction. Moving away or deleting the last member releases the mailbox; deleting one grandfathered member does not release the other members' claim. Unconfirmed accounts reserve their mailbox as existing Supabase email uniqueness already does. No existing account, entitlement, password, or recipient address is modified by bootstrap.

The migration takes a short write-blocking lock on `auth.users` during bootstrap. Apply it in a transaction after authorized alias testing finishes. Never disable triggers during normal signup; service-role/admin account creation also observes the policy. Claims use RLS with no client policy and all API-role grants revoked; the trigger uses SECURITY DEFINER with an empty search path. The optional hook alone is not the concurrency guard.

For usable rejection copy, enable `public.before_user_created_mailbox_guard` as Supabase's Before User Created Postgres hook after applying the migration. It returns a 422 with sign-in/reset guidance; only `supabase_auth_admin` can invoke it. Existing hook configuration must be inspected and composed, not overwritten blindly. The database trigger is mandatory enforcement and may surface Supabase's generic database-save error for a concurrent race or when the hook is not enabled. This design does not try to map every generic database error to duplicate email in the application.

Official references: [Before User Created](https://supabase.com/docs/guides/auth/auth-hooks/before-user-created-hook), [Auth Hooks](https://supabase.com/docs/guides/auth/auth-hooks), [Auth database errors](https://supabase.com/docs/guides/troubleshooting/dashboard-errors-when-managing-users-N1ls4A).

Validation must use a disposable database, never production account inserts. SQL scenarios cover normalized matching, exact delivery address, alias/base/case duplicates, different domains and dotted custom-domain local parts, email-change rejection, same-mailbox edits, NULL transitions, deletion, hook responses and grants. The runner also covers historical duplicate bootstrap, failed-transaction rollback and two simultaneous clients competing for the same mailbox.

Validation on September 10 passed against an isolated PostgreSQL 18.4 instance using two independent database connections. The runner is `scripts/test-auth-mailbox-claims.mjs`; it requires a new, empty localhost database named `ielts_auth_guard_test_*` through `TEST_DATABASE_URL` and refuses other targets. Temporary embedded PostgreSQL tooling was installed outside the repository; no project runtime dependency was added. No live migration has been applied by this work.
